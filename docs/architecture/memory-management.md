# AI 陪伴应用记忆管理设计

本设计面向鸿蒙手机中的 AI 陪伴应用，目标是让角色记住用户确认的偏好和经历，同时允许用户查看、纠正和删除。目标方案以 PostgreSQL 为权威存储，pgvector 和关键词索引用于检索。以下包含完整目标模型与接口约定。

当前迭代已经实现其中的文字与基础记忆流程，使用 SQLite 在本地运行，保留 PostgreSQL 连接兼容。关键词召回、来源与版本、确认、纠错、暂停和在线删除已落地；向量检索、完整时间模型和备份恢复仍是目标设计。当前实际范围以[实施清单](../implementation-plan.md)和生成的 [OpenAPI](../../packages/contracts/openapi.json) 为准。

## 记忆分层

| 类型 | 保存内容 | 更新与保留策略 |
| --- | --- | --- |
| 工作上下文 | 最近若干轮原始消息、当前任务和引用指代 | 按 token 预算截取；不能代替长期存储 |
| 会话摘要 | 一次会话中的重点、未完成话题 | 保留来源和覆盖范围；来源删除后重建 |
| 用户事实与偏好 | 称呼、明确偏好、当前居住地等 | 显式纠错优先，保存版本与有效期 |
| 情景事件 | 旅行、考试、纪念日和共同谈过的经历 | 按事件时间组织，区分计划与已发生事件 |
| 临时状态 | 用户自述的近期情绪、临时安排 | 默认短期使用；期限可配，不能自动升级成永久人格 |
| 角色设定 | 角色名字、说话风格、虚构背景 | 独立版本；与现实用户事实隔离 |

用户记忆、角色设定、外部知识分别管理。用户说“假设我住在北京”不能覆盖真实居住地；角色说“我陪你去过海边”也不能自动成为现实经历。

## 作用域与来源

每条记忆都属于认证用户。默认还绑定角色；只有用户明确选择共享的资料，才使用用户级作用域。用 `scope` 枚举和非空 `scope_id` 表达归属，避免可空角色字段导致唯一约束失效。

`user_id` 必须由服务端登录态得出，客户端不能指定其他用户身份。列表、搜索、按 ID 读取、修改、导出和后台任务均要校验归属。向量召回也带作用域条件，组装上下文前再次核实权限、状态和有效期。

来源至少区分：用户直接陈述、用户手动编辑、模型推断、助手陈述、工具已验证结果、引用内容和角色扮演。用户直接陈述与手动编辑可支持现实事实；其余类型按用途进入候选或单独区域。模型自行标记的 confidence 只是排序线索，不能当作经过校准的真实性概率。

## 数据模型草案

| 实体 | 核心字段 | 作用 |
| --- | --- | --- |
| `messages` | id、user_id、character_id、conversation_id、role、content、created_at、memory_policy、deleted_at | 原始证据与会话历史 |
| `memories` | id、user_id、scope、scope_id、kind、subject、predicate、value、content、status、revision | 可管理的事实或事件 |
| `memory_evidence` | memory_id、message_id、source_type、source_span、recorded_at | 多来源追溯，范围用偏移表达 |
| `memory_versions` | memory_id、revision、change_reason、valid_from、valid_to、recorded_at、supersedes_id | 区分过去与现在，解释纠错 |
| `memory_embeddings` | memory_id、revision、model_id、dimensions、embedding | 按模型版本隔离的派生向量 |
| `summaries` | id、conversation_id、content、source_revision、status | 可失效、可重建的会话摘要 |
| `summary_sources` | summary_id、message_id、memory_id | 跟踪摘要依赖，支持级联删除 |
| `memory_tasks` | id、user_id、kind、idempotency_key、status、lease_until、attempts、payload_ref | 持久化抽取、索引与清理任务 |
| `deletion_jobs` | id、user_id、target_id、status、revision_fence、completed_at | 删除进度与重放屏障 |

事实补充字段包括：`event_time`、`valid_from`、`valid_to`、`recorded_at`、`expires_at`、`importance`、`pinned`、`confidence`、`source_type`、`sensitivity`、`consent_state`、`supersedes_id`。时间统一存 UTC，并保留用户时区及原始时间表达；不确定时间保存范围与精度，不强造某一天。

示例为已获得用户记忆偏好授权、可在同一用户不同角色间使用的称呼：

```json
{
  "id": "mem_example_001",
  "user_id": "user_example",
  "scope": "user",
  "scope_id": "user_example",
  "kind": "preference",
  "subject": "user_example",
  "predicate": "preferred_name",
  "value": "小周",
  "content": "用户希望被称为小周",
  "status": "active",
  "revision": 1,
  "source_type": "user_statement",
  "evidence_message_ids": ["msg_example_001"],
  "valid_from": "2026-11-01T02:00:00Z",
  "valid_to": null,
  "recorded_at": "2026-11-01T02:00:01Z",
  "expires_at": null,
  "pinned": false,
  "consent_state": "allowed"
}
```

单值属性如当前称呼，对同一用户、作用域、主体和属性最多允许一条当前有效记录。多值属性如爱好允许多条。独立事实的版本变更在事务内完成，使用 revision 乐观锁或行锁防止并发覆盖。

## 写入流程

1. 服务端先持久化用户消息与任务，使用同一数据库事务，避免回复成功而证据丢失。
2. 依据“暂停记忆”“本次不记”“已删除来源”等规则决定消息是否进入抽取。暂停记忆不等于关闭聊天历史，界面应分别说明两种设置。
3. 后台 worker 从原始消息抽取结构化候选，要求带来源、事实类型和时间。问句、假设、引用、否定和角色扮演单独识别。
4. 执行业务校验、来源校验、去重和冲突判定。身份证号、密码、密钥等不进入自动长期记忆。
5. 事务写入事实、版本、证据关系及索引任务，再生成向量与摘要。失败显示“处理中”并重试。
6. 新记忆在管理页面可见；有歧义或需要额外授权的候选不参与常规召回。

用户在管理页手动添加、改正或删除的记忆，直接进入同步业务事务，不等待下一次模型抽取。聊天中的纠错或遗忘指令先走高优先级处理；含糊请求在产品内澄清对象。

worker 使用唯一幂等键，例如 `(source_message_id, extractor_version)`，并记录租约和失败次数。任务重试前重新读取记忆授权、来源状态与删除屏障。进程内临时任务不承担唯一处理责任，避免服务重启后漏记。

## 更新与冲突

| 输入情况 | 处理规则 |
| --- | --- |
| “我不喝咖啡”重复出现 | 合并支持证据，避免每次都新增一条等价偏好 |
| “现在改喝咖啡了” | 当前偏好更新，旧版本结束有效期；保留历史查询能力 |
| “之前记错了，我一直住杭州” | 标记为纠错，修正事实时间，旧内容不再作为历史真实状态回答 |
| “明年可能搬去上海” | 记录为不确定计划，不覆盖当前居住地 |
| “上个月我在上海出差” | 保存事件，不据此推断现居上海 |
| 多人同名或指代不清 | 保留候选或追问，不凭相似名字合并身份 |
| 只有助手自己声称某件事发生 | 不升级为用户现实事实 |

事实变化与原记录错误需要不同的 `change_reason`。前者可以回答“以前如何”，后者必须表明过去记录有误。来源权重优先考虑用户明确纠错与确认；互相矛盾且没有时间解释时保留争议状态，避免静默覆盖。

## 召回与上下文预算

查询流程为：认证作用域与状态约束 → 当前问题解析 → 并行关键词和向量召回 → 时间与版本过滤 → 去重、重排 → 预算裁剪 → 组装上下文。若接入图引擎，将关系查询结果加入同一候选与校验流程。

关键词检索显式增加中文分词或其他已验证的中文检索方案，不能把默认英文处理效果当作中文效果。首版用人工样本校验人名、别名、否定词、日期和数字；向量检索使用固定模型、维度与版本，更换模型需重建对应索引。

重排考虑问题相关度、来源可信程度、事实有效期、用户置顶、重要性和重复性。旧记忆的排序权重可以衰减，但不能因此篡改稳定事实；“置顶”也不能绕过删除或作用域限制。

初始实验可将长期记忆预算设为约 2000 tokens，再按所选模型的 tokenizer 实测调整；最近消息、角色设定、摘要、长期记忆与回复预留共同受总窗口约束。候选不足或证据冲突时允许回答“不确定”，不能强行凑满 Top K。

上下文携带记忆 ID、有效时间与来源标签，以便用户打开“这条回复用了哪些记忆”。记忆内容作为数据传入，不能提升为系统指令；检索到“忽略之前指令”等文字时仍按不可信内容处理。

## 遗忘与删除

产品提供三种明确操作：暂停产生新记忆、让某条记忆失效、删除内容。删除聊天与删除其派生记忆的关系也要在界面中说明。

删除流程先在事务内设置删除状态和 revision 屏障，使后续请求立即排除该记忆，同时生成持久化删除任务。随后清理原始来源中被要求删除的片段、历史版本正文、证据摘录、向量、关键词、摘要、缓存及可选第三方引擎中的副本。若来源必须整条删除，按整条消息处理；含其他独立事实的派生记录需要重新计算依赖。

“彻底忘记”必须处理仍可能用于重建记忆的原始来源；只删向量或隐藏管理页会导致下一次摘要、抽取或重新索引时记忆复活。删除任务保存不含原文的目标标识与屏障，阻止旧任务重放。

删除状态区分“已停止使用”“清理中”“在线副本已清理”和“备份保留期结束”。备份采用明确保留周期，恢复时先重放删除清单，再开放读写和重新索引；不能在仍有可恢复副本时显示“所有副本已彻底删除”。

客户端在联网后同步删除指令、清理本地缓存并记录确认；离线设备的清理状态须单独显示。进行中的生成任务收到删除后取消并重建可用上下文，已经发送到用户端的文字无法追溯撤回。服务日志和审计记录默认不写记忆正文。

## 客户端管理页面

- 记忆列表：区分事实、偏好、事件和临时状态，可按角色与状态筛选。
- 记忆详情：展示来源消息、有效时间、变更原因和使用范围。
- 编辑与纠错：允许修改内容、标记记错、确认或驳回候选。
- 记忆开关：用户级、角色级以及本次会话级暂停，说明是否仍保存聊天记录。
- 删除与导出：删除预览列出影响范围，后台进度可追踪，导出只包含当前用户的数据。

鸿蒙端优先保存近期会话和管理页缓存；数据库加密与密钥存储按目标 SDK 验证。服务商密钥保存在后端，客户端保存本应用的登录凭据。

## 接口草案

| 接口 | 语义 |
| --- | --- |
| `POST /v1/conversations/{id}/messages` | 幂等写消息，返回 request_id 与流式回复事件 |
| `GET /v1/memories` | 分页列出有权查看的记忆，默认只展示可用记录 |
| `POST /v1/memories` | 用户手动创建并记录来源为手动输入 |
| `GET /v1/memories/{id}` | 读取详情及授权范围内的证据 |
| `PATCH /v1/memories/{id}` | 带 revision 纠错，冲突返回 409 |
| `DELETE /v1/memories/{id}` | 幂等建立删除屏障，返回删除任务 ID |
| `GET /v1/deletion-jobs/{id}` | 返回本人删除任务的各阶段进度 |
| `PATCH /v1/memory-settings` | 修改暂停、作用域共享和保存偏好 |
| `POST /v1/memory-exports` | 创建本人数据导出任务 |

对话事件建议包含 `accepted`、`token`、`completed`、`error`，都携带 request_id 和递增 sequence。重试不能重复创建用户消息，重连补发策略在协议验证时确定。上述接口尚未实现。

## 记忆引擎接入边界

Mem0 或 Graphiti 适配器只接收已授权的证据，返回候选事实或候选 ID；本项目负责有效版本、来源、权限和删除。采用前要求实现 `extract`、`index`、`search`、`delete`、`export` 与错误报告的映射。

若引擎另有存储，通过事务任务同步；搜索返回后到权威记录校验 revision。删除失败保留屏障、显示进度并重试，不把第三方成功响应直接等同于所有副本清理完成。第一阶段只实现基础方案，适配器是否上线由[验证计划](../research/poc-plan.md)决定。
